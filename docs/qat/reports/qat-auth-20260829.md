## Harness notes

The in-app Browser pane was not displayed during this run. Two consequences, both affecting **method** rather than results:

1. **Screenshots are unavailable** — the page does not composite frames while the pane is hidden. Evidence is therefore textual: accessibility-tree dumps, `location.pathname`, and extracted page text. This is arguably more precise than a screenshot for assertion purposes, but it means no visual evidence is attached.
2. **Coordinate-based clicks do not land.** Clicking an element by reference left `document.activeElement` as `BODY`, so keystrokes went nowhere and forms appeared to do nothing. This produced three false "no user feedback" observations early in the run, which were **retracted** after the cause was identified.

Working interaction method adopted: focus the target element via a JS selector, type with real key events (so React's `onChange` fires normally), and submit via the form's native `requestSubmit()`. Values were confirmed present in the DOM before every submission.

**Cases QAT-AUTH-02, -03, -04, -05, -11, -12, -13 are deferred**, not failed. They require an unauthenticated session, and signing out mid-run would have invalidated the shared session other test agents were using. They are re-run at the end of the campaign.

## Defects

### QAT-AUTH-10-D1 — Seven admin routes are not gated by middleware and render to unauthenticated visitors  [HIGH]

**Steps to reproduce**

1. Open a browser with no Residio session (or clear cookies).
2. Navigate to `http://localhost:3000/documents`.

**Expected**

Redirect to `/login?next=%2Fdocuments`, consistent with every other admin route.

**Actual**

HTTP 200. The page stays on `/documents` and renders the full admin dashboard shell, including the complete sidebar navigation:

> Dashboard, Analytics, PEOPLE & PROPERTY — Residents, Houses, Contractors & Staff; FINANCIAL — Transactions, Import Statement, Import Email, Invoices & Dues, Generate Invoices, Expenditure; OPERATIONS — Security, Reports, Generate Reports, Financial Overview, Documents, Announcements, Approvals, Capital Projects; SYSTEM — Settings, System

The Documents page body renders its headings, stat cards, and repository panel. Reproduced identically on `/personnel` (which additionally renders the "Personnel & Vendors" directory table header row: `NAME / ROLE  TYPE  CONTACT INFO  ACCOUNTABILITY  STATUS  ACTIONS`), `/announcements`, `/projects`, `/expenditure`, `/analytics`, and `/notifications`.

**Data exposure assessment**

No resident or estate data was returned to the unauthenticated session. All stat cards read `0` and the tables rendered empty states ("No documents yet"). Row-level security appears to be holding at the data layer, so this is currently **structural exposure** — the admin information architecture, module names, and page chrome — rather than a data breach.

**Why this is still HIGH rather than MEDIUM**

The same missing configuration governs *authenticated but under-privileged* users. Both gates that would stop them are absent for these paths:

- `routePermissionConfig` at [src/middleware.ts:8](src/middleware.ts:8) omits all seven routes, so no permission check runs.
- `adminOnlyRoutes` at [src/middleware.ts:25](src/middleware.ts:25) omits all seven, so the resident-blocking rule does not apply either.

For `/documents` and `/announcements` this is a straightforward wiring omission: [src/lib/auth/action-roles.ts:181](src/lib/auth/action-roles.ts:181) **does** declare them as permission-gated —

```
'/documents': [PERMISSIONS.DOCUMENTS_VIEW],
'/announcements': [PERMISSIONS.ANNOUNCEMENTS_VIEW],
```

— but the middleware's own copy of the table never picks them up. `/personnel`, `/projects`, `/expenditure`, `/analytics`, and `/notifications` appear in **neither** table, so they were never gated at all.

Whether a `resident`-role account can read data on these pages depends entirely on per-table RLS, which was not exercised in this pass (cross-role testing was out of scope). That is the unquantified risk, and it is the reason this is filed rather than logged.

**Suspected fix location**

[src/middleware.ts:8-28](src/middleware.ts:8) — derive `routePermissionConfig` from `ROUTE_PERMISSIONS` instead of hand-maintaining a second copy, and add the five ungated routes to both `ROUTE_PERMISSIONS` and `adminOnlyRoutes`.

**GitHub issue**: filed — see the defect register in [README.md](../README.md).

## Why automation missed QAT-AUTH-10-D1

`e2e/auth.spec.ts` TC1.4 ("Unauthenticated access to dashboard redirects to login") tests exactly one route:

```ts
await page.goto('/dashboard');
await page.waitForURL(/\/login/, { timeout: 10000 });
```

Because it asserts against a single known-good path, it passes while seven sibling routes go ungated. A table-driven variant that iterates every entry in `ROUTE_PERMISSIONS` plus `adminOnlyRoutes` would have caught this, and would keep catching it as routes are added. Worth adding alongside the fix.

Separately, this run's early false observations about missing login error feedback are contradicted by TC1.3, which asserts `[role="alert"]` becomes visible on invalid credentials and matches the `<Alert variant="destructive">` in the page source. That corroborates the retraction above.

## User enumeration: clean

This was the case most worth running, because the login page surfaces `signInError.message` from Supabase verbatim — provider-controlled wording is exactly where enumeration leaks tend to appear.

| Attempt | Message |
|---|---|
| Wrong password on a **real** account (`admin@residio.test`) | `Invalid login credentials` |
| Correct-format password on a **non-existent** account | `Invalid login credentials` |

**Identical, word for word.** An attacker cannot distinguish a registered address from an unregistered one through the login form. The forgot-password flow is equally tight — the same generic "Check your email" success state regardless of whether the account exists.

Both are genuinely correct, and worth recording as passes rather than silence.

## QAT-AUTH-14 — blank page at `/auth/verify-2fa` when signed out  [LOW]

Unauthenticated, the route renders nothing: `document.body.innerText` length **0**, no redirect, URL unchanged. The only visible element is the floating chat widget. Reproduced twice.

The first attempt also logged two `400` resource errors with an aborted `GET /login?_rsc=…`, consistent with a redirect to `/login` being started and abandoned.

**Authenticated, the same route correctly redirects to `/dashboard`** — verified separately. So the route handles the has-session case and not the no-session case, where every other protected route redirects to `/login`.

**GitHub issue**: [#125](https://github.com/meggarmind/RESIDIO/issues/125)

## Observations recorded but not filed

**Password minimum differs between register (12) and login (6).** `/register` enforces "Password must be at least 12 characters"; `/login` validates `min(6)`. This is not a security weakness — login's rule is a client-side form check, not policy, and the server authenticates against the real credential either way. It also has to tolerate existing accounts created under older rules (the seeded `password123` is 11 characters). Recorded as an inconsistency in user-facing messaging, not filed.

**`/forgot-password` relies on native browser validation for malformed emails.** Submitting `not-an-email` produced no app-rendered message; the block came from the browser (`validationMessage: "Please include an '@' in the email address…"`). It is invisible to a DOM read and inconsistent with the zod-plus-inline-message pattern used everywhere else, but the input is still correctly rejected. Recorded, not filed.

Both are the kind of finding that inflates a defect register without giving a developer anything worth doing.
