## Decisions

### D1 — #558: is expiry intended, and for how long?
- **Options:** 72h for every request type / per-type periods / do not expire
- **Decided:** 72 hours, every request type.
- **Basis:** project docs — `supabase/migrations/20251231032140_add_approval_auto_reject.sql` already encodes 72 hours and the auto-reject note; recommendation recorded on the issue after #559.
- **Reversible by:** changing `APPROVAL_EXPIRY_HOURS` in `src/lib/approvals/create-approval-request.ts` (and the user-facing wording in `notify-requester.ts`).

### D2 — #558: who sets `expires_at`?
- **Options:** `createApprovalRequest` / a column default (migration)
- **Decided:** `createApprovalRequest`; no default, no backfill of requests already pending.
- **Basis:** recommendation — no migration, and a backfill would auto-reject requests the owner never agreed to expire (Residio_Stage had 0 pending rows when checked, so nothing is lost either way).
- **Reversible by:** removing the line; existing rows are unaffected.

### D3 — #558: what runs `process_expired_approvals()`?
- **Options:** new `/api/cron/*` route / `pg_cron`
- **Decided:** a new cron route, `expire-approvals`, hourly, recorded in the System Action Log like the other routes.
- **Basis:** project docs — every other scheduled job is a cron route registered in `docs/deployment/hosting-plan.md`. The Coolify scheduled task must be created by the owner; until then nothing runs it.
- **Reversible by:** deleting the route and the hosting-plan rows.

### D4 — #558: tell the requester when a request expires?
- **Options:** in-app notification / none / email too
- **Decided:** in-app only, "Request expired", through the #559 helper; a notification failure never fails the run.
- **Basis:** owner precedent — #412 handoff of the #262/#290 run (requester notification is in-app only).
- **Reversible by:** removing the notify loop in `src/lib/approvals/expire-approvals.ts`.

### D5 — #558: accept a rare missed notification rather than risk duplicates
- **Options:** read back only the ids due before the RPC / read back by `reviewed_at` window
- **Decided:** keep the ids read before the RPC. A request that expires in the instant between the read and the RPC is rejected but its requester is not told; the window readback would instead notify twice when runs overlap or the function is called by hand.
- **Basis:** recommendation, after blind QA described both races. Documented in the doc comment of `expire-approvals.ts`.
- **Reversible by:** changing the readback filter (one function).

### D6 — #666: which imports may be submitted?
- **Options:** at least one matched row required / any import / matched or intentionally skipped rows
- **Decided:** at least one `matched` row; unmatched rows alongside it are allowed.
- **Basis:** project docs — the import wizard already enforces exactly this ("No matched rows to process, so there is nothing to submit."); the issue asked to enforce the wizard's rule on the server.
- **Reversible by:** relaxing `hasMatchedRows` in `src/lib/imports/submit-guard.ts`.

### D7 — #701: file the over-broad grant on `process_expired_approvals()` instead of fixing it inside #558
- **Options:** revoke in #558 / file separately
- **Decided:** filed #701 under map #290. A revoke is a migration that changes who can call a database function (narrowing, but its own change and its own apply step), and CORE.md §15 says a defect outside scope is filed so a security fix is not hidden in a feature.
- **Basis:** project policy — CORE.md §10 rule 4, §15.
- **Reversible by:** n/a (nothing changed).
