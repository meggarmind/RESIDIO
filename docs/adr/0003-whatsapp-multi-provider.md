# WhatsApp delivery supports multiple providers via runtime configuration, not hardcoded selection

Outbound WhatsApp delivery now goes through a provider registry with two adapters: Meta Cloud API (default) and Twilio, selected by runtime configuration stored in an encrypted database table rather than deployment-time environment variables. This replaces the hardcoded Meta-only approach from ADR-0002.

The reasoning behind ADR-0002 still holds for the default: Meta is the platform every Business Solution Provider wraps, with no per-conversation margin or third-party subscription cost that a BSP would add on top. Meta remains the recommended provider for most estates. What changed: some estates need the ability to choose a provider at runtime and manage credentials from the Admin Dashboard instead of requiring environment variable changes and redeployment. A single hardcoded client could not offer that choice without being expensive to swap out later. The provider registry isolates all Meta and Twilio specifics behind `src/lib/whatsapp/` (mirroring the pattern of `src/lib/sms/`), so swapping providers stays cheap if circumstances demand it.

There is one honest limit: outbound delivery uses a unified interface with the provider registry, but inbound webhook handling is not unified. Meta and Twilio use different signature verification algorithms (HMAC-SHA256 over the raw request body vs HMAC-SHA1 over the URL plus sorted query parameters) and different payload shapes, so each provider has its own webhook route and parser. Everything after the signature check and payload parsing — message routing, state machine, notifications — is shared. Twilio adds per-message cost on top of Meta's rate structure; estates should understand this trade-off when choosing a provider.
