# Release v1.0.0

**Release date:** 13 October 2026. **Release type:** Major (upgrade steps are necessary).

## Summary

This release is mostly security work from a full review of the admin dashboard. Two-factor sign-in is now enforced for users who turned it on. Access checks are stronger on many actions. Payments that an admin has verified are now locked. The app now shows its version in the sidebar. You must do the steps in **Before you upgrade** first.

## Before you upgrade

Two settings are now required. If a setting is missing, the related feature stops and does not run in an unsafe way.

1. Set `DATA_ENCRYPTION_KEY` in the production environment. It has 64 hexadecimal characters. You can use `GMAIL_TOKEN_ENCRYPTION_KEY` instead. If it is missing, users who turned on two-factor sign-in cannot finish signing in.
2. Set `PAYSTACK_WEBHOOK_SECRET` in the production environment. If it is missing, the Paystack webhook returns an error (503) and the app does not record the payment.
3. Make sure you apply these six database migrations to the production database, in this order:
   - `20261012100000_restore_view_security_invoker`
   - `20261012200000_drop_forged_insert_policies`
   - `20261012200100_late_fee_waivers_maker_checker`
   - `20261012210000_lock_down_two_factor_secrets`
   - `20261012220000_atomic_wallet_payment_rpcs`
   - `20261013100000_dashboard_payment_metrics`
4. Do this step after you apply the migrations: run the script `scripts/reencrypt-totp-secrets.ts` against the production database. Do a dry run first. It encrypts the saved two-factor secrets.
5. Check that the two views `security_settings_view` and `visitor_analytics` have the option `security_invoker=true`.

## New features

### Security and access

- Two-factor sign-in is now enforced. A user who turned on two-factor sign-in must enter a code after every sign-in. The app does not force any role to turn it on.
- Two-factor codes and backup codes are stored more safely. The code check also uses the signed-in user and not a user that the browser sends.
- Admin buttons for create, edit, delete and approve now show only to roles that have the permission. This applies to approvals, payments, billing, residents and houses.

### Payments

- A verified payment is locked. You cannot change its amount, payer, house or status.
- An admin with the right permission can now **Un-verify** a payment. The button is on the payment edit page and in the quick view. The app asks for a confirmation and an optional reason.
- A bulk status update now skips verified payments and tells you how many it skipped.

### Dashboard

- The admin dashboard now gets the payment totals from the server. The monthly revenue, the unverified totals and the six-month trend stay correct when there are more than 1,000 payments.

### Administration

- The sidebar footer shows the app version and the short commit code. A **STAGE** badge shows on the staging site and a **DEV** badge shows in development.

## Changes

### Security and access

- A user can no longer change the role or account of a user with a higher rank. The ranking is: super admin, chairman, and then all other roles. Only a super admin can edit a system role.
- Resetting the two-factor sign-in of another user follows the same rank rule.
- A user can only add permissions to a role if the user holds those permissions.
- Reject now works only on accounts that are pending.
- Several actions that any signed-in user could call now need a permission. This covers notification preferences, test email, payment reminders and payment receipts.
- The late fee, invoice generation and email fetch actions no longer let the caller choose to skip the permission check.
- A report that you save to the report history now needs the permission to view financial reports.
- The late fee waiver rule is now enforced in the database. A person cannot approve their own request.
- Only the system can now add entries to the audit log, the late fee log and the invoice generation log. Users cannot add them.
- The Paystack webhook now rejects a request when the secret is not set or the signature is not valid.

### Billing and wallets

- Wallet debits and billing settings changes now need a permission and are recorded in the audit log.
- The wallet payment and reversal actions now run as one step. This stops partial updates.

### Imports and uploads

- Uploaded files are stored under names that the app creates. The app checks the file type and size.
- The logo upload no longer accepts SVG files.
- Spreadsheet uploads are limited to 10 MB.
- A bank statement import reads all rows when it has more than 1,000 rows.
- The PDF statement import now needs the permission to create imports. It also has size, time and row limits.

### Other changes

- All money amounts that an admin enters must now be positive, finite and have at most two decimal places. This covers petty cash, invoice corrections, expenses and late fee waivers.
- Search boxes now handle special characters safely.
- Edit forms now save only the fields that the form shows.

## Fixed problems

- The household list and housemate receipts failed for some houses. They now work.
- The generate invoices dialog now works with the keyboard and with screen readers.
- Icon buttons now have names for screen readers.
- The approvals and payments pages now show an error with a retry button when data fails to load. Before, they showed an empty list.
- Large pages load faster. The move-out wizard and the spreadsheet reader now load only when you use them.
- Pages that need a list of residents for a menu now load only the names and codes.
- The notification bell loads its list only when you open it.

## Resident portal

- The wallet top-up window no longer credits the wallet by itself. It shows "Payment received. Your wallet will update once it is confirmed."

## Behind the scenes

- The app was updated to Next.js 16.4.0 and the spreadsheet library was updated. The security audit now shows no known problems in production packages.
- The pull request check is faster and runs before a pull request opens.
- Tests now cover the new access rules and the new database rules.
